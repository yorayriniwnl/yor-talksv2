## Transactional email and marketing

The repository's send call graph contains three email templates: email verification, password recovery and one-time sign-in code. They invoke `EmailService.sendEmail`; auth calls invoke only those methods. No newsletter enrollment, promotional sender, marketing subscription list or campaign dispatcher was found. Transactional templates do not require a fictitious marketing unsubscribe mechanism to be introduced. This is a product-behavior finding, not a determination of every jurisdiction's email law.

`EmailService` sends recipient address, subject, HTML and optional plain text to the fixed Resend API when configured. Credentials do not enter intentional email logs; those contain a short deterministic recipient hash and byte count/status. Hashes remain pseudonymous and potentially guessable; they must not be described as anonymous. Production errors fail closed rather than simulate delivery. Local tests/development may simulate mail without sending it. See `services/email-service.ts:83`, `services/email-service.ts:122`, `services/email-service.ts:142`, `services/email-service.ts:160` and `email-service.test.ts`.

If promotional email is introduced later, it requires explicit subscription records/consent, suppression enforcement, verified unsubscribe behavior and appropriate provider/header acceptance before it can be sent. Authentication/security delivery must remain independent from that future marketing preference.

## Account deletion and export boundary

`DELETE /users/me` requires authenticated subject identity, the literal confirmation `DELETE` and current password confirmation. The API uses the authenticated subject rather than a caller-supplied target user. It rechecks the locked password snapshot inside the deletion transaction. Restricted accounts retain reviewed export/deletion/security routes. The export streams bounded allowlisted collections through a read-only repeatable-read snapshot and handles cancellation/rollback; another user's private credentials, contact choices, shipping data and read timestamps are not general participation data.

The deletion transaction revokes the latest guardian authority, minimizes financial/commerce personal fields, records legacy media cleanup holds and durable retry work, prunes embedded relationship/reaction actors and counters, removes actor-attributed notices, preserves other members' group messages and deletes the departing author's messages/user row. Normalized dependent rows use reviewed FK behavior. The lifecycle worker retries Redis device/challenge cleanup and provider media cleanup. Completed durable jobs clear their payload, but deduplication IDs and retained diagnostics still need the operator's retention decision. This is not a guarantee that every provider/backed-up copy disappears synchronously when the HTTP request returns.

## Unresolved launch decisions

1. Approve the real operator, jurisdiction intersection, processor contracts/regions, rights contacts and current privacy/terms wording. Do not claim the unavailable assurance adapter is a verified provider integration.
2. Approve an explicit category-by-category retention schedule for profiles/content, expired retained messages, eligibility/guardian evidence, grievances/reports, analytics, payment events/financial records, durable job diagnostics, logs and remote backups. Existing expiry and bounded queues are narrower safeguards.
3. Define actual provider erasure/retention obligations, a measurable cleanup service level, dead-letter response and legacy URL ownership resolution. Synthetic idempotency tests cannot close Cloudinary/Resend/Google/payment-provider acceptance.
4. Define restore-after-erasure handling, deletion/restriction reapplication, backup access and scheduled remote expiry. Do not state that account deletion immediately deletes historical off-host archives.
5. Complete broader correction/restriction/objection/complaint procedures and moderation remedy/notice/review workflow, with qualified legal and operating approval. The export/delete endpoints alone do not implement every rights process.
6. Approve deployment log collection/access/retention and review historical verification-path/provider capability logs and old nonexpiring Redis audit indexes. No production cleanup was performed in this task.

These are explicit launch blockers or policy decisions, not claims that implementation alone establishes GDPR, DPDP or any other legal compliance.
