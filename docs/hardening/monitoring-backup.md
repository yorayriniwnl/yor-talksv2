## Monitoring repair and runtime evidence

The previous Compose service passed `--config.expand-env` to Alertmanager v0.28.1 and mounted YAML with unresolved environment placeholders. The exact runtime does not support that flag. `ops/prometheus/Dockerfile.alertmanager` now copies the pinned v0.28.1 binaries into a Node 24 runtime, renders configuration before startup, checks it with the same `amtool`, then starts Alertmanager. `render-alertmanager.mjs` validates required values, rejects unresolved placeholders and control characters, requires HTTPS outside an explicit isolated local-receiver test, and serializes scalar values with JSON quoting (valid YAML). URL credentials are rejected; the password stays in the read-only mounted secret file. Generated configuration uses a protected directory and mode 0600 and is never printed.

The renderer follows the pinned runtime's [official webhook configuration](https://raw.githubusercontent.com/prometheus/alertmanager/v0.28.1/docs/configuration.md), including file-backed HTTP authentication. Monitoring interfaces remain internal to Compose. Production receiver reachability and delivery to an operational owner remain unverified.

`ops/prometheus/acceptance.mjs` executes actual Alertmanager 0.28.1 and Prometheus 3.5.0 binaries, downloaded from their official release archives and checked against upstream SHA256 manifests. The final renderer also rejects ASCII control characters and Unicode line separators that YAML can fold. It validates the repository Prometheus configuration and alert rules, rejects invalid configuration, starts Alertmanager, checks readiness, verifies an authenticated Prometheus scrape, delivers both firing and resolved alerts to a local authenticated receiver, then verifies invalid receiver authentication is rejected. Final native execution exited **0**; evidence is `monitoring-acceptance-final.log` in the private temporary evidence directory and runtime logs in `yor-monitoring-fNXNML`.

CI now repeats this exercise with the pinned Linux binaries. `production-config:check` additionally rejects the unsupported flag and checks the runtime acceptance wiring, but its string checks are not runtime evidence. CI builds the rendered Alertmanager image and its container smoke checks readiness. This working copy has not been submitted to CI, and this Windows host has no Docker Engine; image execution remains open. File-backed Compose secrets preserve host permissions; the runbook now requires private reader ACLs and actual default-user checks for API, Prometheus and Alertmanager. Existing Alertmanager volume ownership must also be checked before changing its runtime user. Those host checks were not executed here.

New lifecycle alert rules cover availability, overdue work, stalled handlers, expired leases, dead letters, stale cleanup progress and recovery failures. Their syntax passed the pinned `promtool`; delivery of real lifecycle alerts through the production receiver remains an operator gate.

## Backup and restore repair

`lib/db/scripts/backup-database.sh` now cleans decrypted temporary files on every exit, records failed backup metrics even for early failures, uses unique encrypted archive names, and restores with `pg_restore --single-transaction`. Restore requires an explicit `RESTORE_TARGET_DATABASE` equal to the connected database, rejects the archive's source and system databases, and refuses existing application objects. The production image normalizes shell line endings. The option order for `psql` was repaired after native execution showed that placing options after the database URL caused the Windows runtime to ignore them.

`ops/backup/acceptance.mjs` creates unique synthetic source/target databases after checking the explicit loopback database identity. It migrates the source, seeds two synthetic users and a message, encrypts with age, uploads/retrieves through a local rclone remote, compares encrypted checksums, decrypts and restores to a separate empty target. `api-server/src/scripts/backup-fixture.ts` verifies actual authentication, message history, credential revocation, relationships, constraints and migration ledger state after restore.

Negative cases cover corrupt archives, wrong keys (verification and restore), failed uploads with failure metrics, wrong target names, source targets, nonempty targets outside `public`, repeated restore into the populated target and an actual permission-denied `pg_restore` failure. The failed restore must reach `pg_restore`, and its transaction must leave no partial application tables. Each command's private output is retained in the drill directory.

After the final independent strict-empty guard repair, expanded native execution exited **0**, with **3,854 ms** restore command time, logs at `backup-acceptance-guard-final.log` and `yor-backup-vOCoA5`. User functions in public/system schemas, type-only, empty custom-schema and public extension targets are refused with the existing objects preserved. Earlier expanded executions also passed with 5,763 and 1,737 ms restore times; they are historical, narrower evidence. That timing covers a tiny synthetic restore, not a production recovery objective. Earlier successful drills and repaired failures remain retained; they are not substituted for the final expanded acceptance.

CI now builds and runs the real backup image (`BACKUP_USE_DOCKER=true`) using the same acceptance program. Native execution on this host establishes actual encryption/database/application behavior but does not establish Linux image execution or off-host transport. Test databases and login roles remain in the private test cluster for inspection; no customer or public database was seeded or restored.

Production acceptance requires an encrypted off-host artifact retrieved through approved access, an isolated restore, representative application verification, measured recovery point/time against owner-approved RPO/RTO, and named responsible operators. None of those approvals or production facts has been inferred.

## Deployment and rollback

Apply reviewed migrations before starting the new API/workers. Fresh bootstrap uses checked-in `lib/db/scripts/production-base.sql` in a transaction with a verified empty schema; existing databases use additive, repeatable migrations. Runtime schema push and force operations were removed. Fresh, representative legacy and failure/rollback tests are linked in [message evidence](message-integrity.md).

Ordinary `pnpm smoke` now requires healthy database/Redis/notification/lifecycle workers, lifecycle progress, a decoder and `details.media.ready=true`. Only loopback CI with `CI=true` and `SMOKE_SYNTHETIC_PROVIDERS=true` may exercise the explicitly unavailable synthetic-provider stack. This exception remains distinct from core media acceptance. Tests in `tests/release-readiness.test.mjs` assert these boundaries.

Application rollback requires a compatible previous image. It must preserve credential epochs and atomic OTP authority, current-message/media authorization, nullable legacy group references, the public grievance allowlist, durable job fencing and delivery state. Leave additive tables/columns and financial/media evidence in place. Restoring an older database is a separate approved recovery operation, never an automatic application rollback step. Quiesce writes and review recovery consequences before a separate restore or cutover.
