# Email sign-in credential and concurrency repair

This is working-copy evidence on `codex/media-lifecycle-20261006`, based on
commit `ba31c9fd443659bcacc9d2c8760086adf63ee082`. It does not certify the
committed baseline, a deployed service, or provider email delivery.

The 7 October review found unversioned email-code state, independent
GET/SET/DEL operations, lost incorrect attempts, multiple successful sessions,
and pre-revocation codes becoming sessions at a newer credential epoch.

`api-server/src/services/auth-service.ts`,
`api-server/src/repositories/redis-repository.ts`, and the new
`api-server/src/repositories/auth-challenge-scripts.ts` now:

- Reserve one code atomically with NX and an absolute expiration. State binds
  its schema version, random challenge ID, account ID, normalized email,
  issuance `authVersion`, code hash, attempts, and expiration.
- Validate both service and Lua state; malformed, legacy/unversioned, expired,
  exhausted, deleted-account, and stale-epoch credentials fail closed.
- Count incorrect guesses atomically, saturate at five, and retain the exact
  original Redis expiration. Incorrect submissions cannot extend a code's life.
- Compare the original challenge ID before consuming/updating state or deleting
  a failed email reservation. Late requests cannot alter replacement codes.
- Transfer a correct email first factor into one linked device approval.
  Concurrent submissions receive the same challenge, whose expiry and epoch
  remain those of the email code. Valid TOTP fallback and approved-device
  completion consume that same authority atomically; neither can duplicate it.
- Validate the current account epoch for approval/completion, retain atomic
  device-number attempt accounting, and keep TOTP requirements.

The existing conditional PostgreSQL `UserRepository.recordLogin` update is
the session-creation credential boundary. It requires the issuance epoch and
an active account. Revocation before that update prevents session creation.
Revocation after the update can leave a late Redis session, but both tokens
retain the old epoch and HTTP/refresh authentication rejects them. Best-effort
Redis cleanup is not the revocation boundary.

Successful consumption is final. If the subsequent PostgreSQL update, Redis
session write, or response preparation fails, the code/approval remains burned.
The client must request a fresh code and complete MFA again. Restoring consumed
state would make an ambiguous completion replayable.

`55447`, isolated database `yor_hardening_auth_20261007`, and real Redis

Result: **34 passed, 0 failed, 0 skipped, exit 0** (11.68 seconds). The new OTP
file contributes 17 top-level cases plus nine nested corruption/expiry cases.
After strengthening its target-identity/Redis-version guard, its focused rerun
passed **26/26, zero skips, exit 0** (6.66 seconds).

Coverage includes 30 concurrent requests, 30 concurrent correct redemptions,
exact attempts/expiry under concurrent guesses, replay, corruption, expiration,

## Rollout and rollback

No PostgreSQL migration or API contract change is needed. The implementation
requires Redis 7 features already provided by production's Redis 7 image.
Drain old API replicas before exposing the repaired email-code endpoint; old
replicas can still redeem legacy state through the former path. Existing old
email codes/device challenges safely fail after rollout; users request a fresh
code after expiration. Existing ordinary sessions retain their database epoch.

An older application image is incompatible with this security guarantee.
Rollback must disable email-code sign-in/approval completion or keep the repaired
authentication implementation. Drain older replicas and invalidate all relevant
Redis challenges/sessions under an approved operator procedure; retaining the
database epoch checks remains mandatory. Do not restore an older database as an
application rollback step.

Real Resend delivery, approved accounts, Google sign-in and deployed cookie/origin
acceptance remain separate external gates. Local synthetic dispatch does not
establish them.
