## Architecture verified in source

The persistent backend starts Express HTTP and Socket.IO on the same server, connects PostgreSQL/Redis, and starts notification, feed and durable lifecycle workers. PostgreSQL stores canonical data and durable cleanup/payment jobs; Redis holds expiring authentication/session state, rate limits, notification queues and realtime fan-out. Readiness requires the database, compatible Redis, a notification worker heartbeat and the lifecycle worker; optional media diagnostics do not silently enable unavailable media.

The Vercel HTTP entry imports the bundled Express handler and explicitly does not run a durable Socket.IO listener or worker. A Vercel web/API deployment therefore needs a separately operated persistent realtime/worker deployment sharing the accepted database and Redis. The Compose topology instead starts workers in the persistent API process; a separate worker service is optional when that API process is running.

Production Compose keeps PostgreSQL and Redis on an internal network and does not publish their ports. Redis has a password and append-only persistence. API and web publish loopback-only host ports for a Caddy edge proxy. API runs as the `node` user with a read-only filesystem, temporary `/tmp`, all Linux capabilities dropped and no-new-privileges. Migration has an isolated owner URL and provisions a distinct restricted runtime role. Monitoring endpoints are internal. Secret files are mounted for metrics, alert delivery and rclone, with Linux permission validation in CI. Source `.dockerignore` excludes environment files, keys, `.git`, build artifacts and known CI secret fixtures. Base images are version tags, not immutable digests; deployed image scanning and reviewed digest promotion remain operator controls.

Caddy's example routes `/api` and `/socket.io` directly to the loopback API, preserving the intended single trusted proxy hop. This topology is a security assumption: adding a CDN/load balancer requires explicit trusted-source configuration and spoofed-forwarded-IP tests. Off-host PostgreSQL/Redis need their provider's TLS and ACL settings; the internal Compose plaintext links are not evidence that an external managed connection is protected.

## Frontend/operator interface contract

For Vercel web hosting, configure the frontend's realtime origin to the approved persistent backend (`VITE_REALTIME_URL` / existing frontend configuration contract) or provide an edge proxy capable of forwarding `/socket.io` HTTP polling and WebSocket upgrades to that backend. API requests must reach the same approved backend/database security boundary. The public transport endpoint must return a valid Engine.IO open packet for an allowed origin, reject an untrusted origin and reject cross-account room joins/events after authentication. The web owner must test reconnect/session-revocation behavior; the backend's authorization tests remain independently executable. No frontend file was modified for this audit.

Before a future approved release, record a commit-to-image/deployment mapping and run the full container/readiness/provider acceptance checks against that exact artifact. This audit authorizes no production deployment and does not convert inaccessible infrastructure into a passing gate.
