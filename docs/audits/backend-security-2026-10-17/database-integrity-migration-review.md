# Database Integrity and Migration Review

Audit date: 2026-10-18 (Asia/Calcutta). Scope: PostgreSQL schema, migration ordering, deletion/export integrity and disposable migration verification. Source baseline `62920ad`, branch `audit/backend-security-20261017`. This patch replaces one existing trigger function through the replayable media migration; it adds no table/column, destructive DDL or data rewrite. No production DDL or data change was executed.

## Architecture and invariants

Drizzle defines the base schema under `lib/db/src/schema`. `lib/db/src/index.ts` wraps `pg.Pool` with Drizzle and propagates explicit publication transactions through `AsyncLocalStorage`. Connection timeout is bounded; idle connections are timed out; arbitrary pool error details are not logged. TLS verification is configurable, and actual hosted TLS/access restrictions require operator evidence. The pool defaults to the driver's size limit; no performance change was made without workload evidence.

`migrate-production.mjs` requires an explicit URL, a unique contact-shield secret and distinct runtime credentials. It preflights runtime-role ownership/privileges before bootstrap. Empty public schemas receive a base Drizzle push; nonempty incomplete schemas fail rather than force a destructive push. Complete schemas use the beta/additive migration path and then runtime grants.

`migrate-beta.mjs` acquires an advisory lock, uses a five-second lock timeout, repairs additive historical tables/indexes, detects duplicate ledger references before unique settlement protection, builds trigram search concurrently, and calls `migrateRelease`. Release changes use a transaction. The full beta history is not one atomic transaction: an interrupted run can leave completed earlier additive changes and is designed to rerun. The beta script allows a local development URL fallback; production operation must use the stricter production wrapper.

Release migration order is: authentication/reset and moderation/job primitives; nullable retained financial FKs; premium/checkout/dispute invariants; shared-history retention; canonical media and triggers; eligibility/contact/group constraints; export indexes; versioned terms history. Media/reference and content writes must use the same transaction. Retained history FKs use `ON DELETE SET NULL`; purely account-owned records cascade. Ledger reference uniqueness and provider-order/payment checks protect reconciliation idempotency.

`configure-runtime-role.mjs` creates a dedicated login without superuser/create-db/create-role/replication/bypass-RLS privileges, rejects unrecognized existing roles, ownership/membership or excessive grants, and grants only table DML, sequence use/select and schema usage. It revokes PUBLIC schema/database creation and TEMP privileges in this dedicated application database. These operations are significant provisioning actions and were not applied to production.

### DB-01 migration review

The migration change is limited to the existing message-hiding trigger's expiry predicate. The soft-deletion branch, entity ownership, reference deletion target and current trigger wiring remain unchanged. PostgreSQL checks the native expiry type at runtime: timezone-less values are converted from the application's UTC wall-clock convention; timezone-aware values remain instants. `clock_timestamp()` makes an update honor actual expiry even if its transaction began earlier. The same correction is applied to the runtime cleanup service's message/story reference sweeps, preserving the three retained-highlight representations. No retained row is backfilled or deleted by applying the function definition. The existing media migration always redefines the function on rerun, so no destructive table migration or new release marker is needed.

Review plan submitted to the root auditor before execution: inspect the predicate and TEMP-only regression; apply the existing migration runner only to the disposable PostgreSQL database; run six trigger cases and the affected media lifecycle/publication regressions; repeat clean/idempotency validation in the separate synthetic production-runner database. Do not reconstruct or delete historical production references without a separately reviewed ownership/content recovery plan.

After root review, the exact pnpm 11 `--filter @workspace/db migrate:beta` command ran only against `audit@127.0.0.1:55432/yor_backend_audit` and exited 0 (`evidence/migration-media-fix.txt`). The six new trigger cases, six new actual-cleanup cases and all 23 eligibility/media integration cases passed: **35 passed, 0 failed, 0 skipped**, 11.00 seconds (`evidence/media-expiry-fix-tests.txt`). This includes the two attachment-expiry scenarios that failed before the fix. UTC, Asia/Calcutta and America/New_York are tested with both timestamp storage types. Trigger tests cover expiry after transaction start; cleanup tests prove future and retained-highlight media never reaches provider deletion while actually expired/soft-deleted media does.

## Disposable migration execution

The root audit provisioned a native PostgreSQL 16.14 instance at loopback port 55432 with database `yor_backend_audit` and synthetic owner `audit`. The root agent executed the exact pnpm 11 workspace command `--filter @workspace/db migrate:beta` twice, with `NODE_ENV=test`, the explicit loopback database URL, local Redis and a synthetic contact-shield key. Both the clean migration and immediate repeated migration completed successfully. Captured evidence: `evidence/migration-clean.txt` and `evidence/migration-repeat.txt`. No production connection string was used.

The stricter production runner was also executed on a separate synthetic database: `evidence/migration-production-clean.txt` and `evidence/migration-production-repeat.txt` both end with `Completed successfully`. `evidence/runtime-role-integration.txt` records fresh/upgrade CRUD, sequences/default grants, isolation and DDL/role/database denial, plus rejection of unexpected existing roles, grants and memberships unchanged. These are local runtime-role checks; they do not inspect a hosted production database.

This confirms current clean installation and idempotent rerun of the additive history and local production-runner provisioning. Legacy media fresh/repeat/v1-followup fixtures also passed in the captured serial integration run. A rerun of a current schema alone is not proof of every historical upgrade. Actual managed PostgreSQL access restrictions, off-host encrypted backup/restore and performance on production-sized data remain separate gates unless explicitly marked with current executable evidence in the final report.

## DB-05 analytics timezone correction

The initial full API run exposed duplicate daily primary keys such as `(2026-10-16 05:30:00, navigation)` on the synthetic cluster, whose session timezone is Asia/Calcutta. Fresh Drizzle schemas store `date` and `occurred_at` as timestamps without a timezone, while historical schemas may use `timestamptz`. The raw rollup cast UTC bounds to `timestamptz` and PostgreSQL then interpreted or assigned wall timestamps using the current session zone. Its Drizzle deletion used a UTC wall midnight key, so it could not replace the shifted row on retry. This also affected which boundary events entered the daily count and the subsequent quality comparison.

The existing advisory-lock transaction now sets **LOCAL** timezone to UTC before its delete/insert. This preserves correct casts for both timestamp representations and automatically restores the original pooled connection setting at commit/rollback. It rebuilds aggregates within the requested UTC day, repairing shifted keys in that day while preserving adjacent days and all raw events. The post-rollup quality query explicitly interprets timezone-less values as UTC and preserves timezone-aware instants, so it remains correct on a separately selected non-UTC connection. No schema change, new migration, production purge or disabling of analytics authorization was needed.

New regression fixtures shadow only three analytics tables on a private checked-out connection. They test both timestamp types in Asia/Calcutta and America/New_York (including a daylight-saving transition date), events immediately before/at the start and end boundary, repeated rollups, successful durable job state, exact processed counts, shifted aggregate repair, preservation of an adjacent day and raw rows, and restoration of the original session timezone. Before the fix, **2 fresh-schema cases failed and 2 legacy cases passed**. After the fix, the new cases and existing analytics integration/unit tests total **15 passed, 0 failed, 0 skipped**, 4.87 seconds. Existing tests retain four concurrent rebuilds and deliberate database-trigger failure/corruption tests. Their reads now use the real service API, and cohort assertions compare exact deltas against the captured baseline so unrelated existing synthetic rows cannot invalidate reruns.

Applying this code does not reconstruct aggregates already shifted into another day. If operators find evidence that the old code ran in a non-UTC deployment, regenerate the affected retained date range from canonical raw events through a reviewed operational procedure. This audit performed no such production operation and does not assume that expired raw source events can be recovered.
