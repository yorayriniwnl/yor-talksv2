## Implemented residual fixes

1. Google Identity Services now loads only after the person chooses **Continue with Google**. A local disclosure describes the resulting provider contact. Password/email-code paths remain available, and provider retry/resizing remains implemented.
2. Registration and reacceptance distinguish accepting Terms/Community Guidelines from acknowledging the Privacy Notice. Optional analytics and marketing remain separate.
3. Reacceptance focuses the missing checkbox, associates its error, retains the choice after failure, blocks duplicate requests, and reports a server terms-version mismatch while the existing route gate remains closed.
4. Successful acceptance previously changed the account's gate state while leaving the URL at `/consent`, which the protected route table did not map. It now navigates home after confirming the returned version, allowing the existing eligibility/onboarding gates to run.
5. Every telemetry send path uses the same current consent/eligibility check. Withdrawal aborts pending fetches and clears queued events; late responses cannot mutate a subsequent consent/session queue; overlapping flushes cannot send the same batch concurrently. A request already received by a server cannot be recalled by client abort.
6. Settings reads back the stored analytics choice instead of claiming success after a storage failure, announces a failure, and reflects a withdrawal from another tab. An ineligible account can withdraw its own previously saved choice without being allowed to grant a new one; a saved choice never bypasses the separate active-collection eligibility gate.
7. Grievance name/URL minimums and URL/email/description maximums match the existing API contract. Requests trim the submitted fields. The ticket lookup validates/normalizes its identifier and focuses invalid input. Submission and lookup block duplicate in-flight actions.
8. Grievance intake explains emergency limitations, ticket privacy and unnecessary secret/identity-document avoidance. A failed response no longer claims that a retry is necessarily safe: the existing endpoint has no idempotency contract.
9. Privacy text explains account-export exclusions and why unbound guest grievance/verification records require verified support.
10. Legal configuration trims identity values and validates readily verifiable syntax. Legal/grievance screens explicitly identify incomplete configuration as a public-release blocker; legal text wraps long configured values.

## Permissions and user controls

Settings uses existing server privacy, notification, export and account-deletion endpoints. Deletion still requires a current password and the explicit `DELETE` confirmation; it does not claim instant erasure of backups, retained records or queued external-media cleanup. Account export excludes authentication material and unrelated private records. No export or deletion endpoint was invented. Google sign-in requires an existing account in the inspected backend; registration stores a password hash. People who no longer know their current password may need the password-reset flow before deletion; no credential bypass was added.

Camera/microphone requests appear in explicit recording/call tools; contact selection uses the browser contacts picker where supported. Push notification permission and device subscription have distinct browser and account controls; implementation and regression details are in the permissions/accessibility reports. No optional email-digest or marketing preference was invented because the inspected beta does not enable it.

## Verification and limits

`pnpm --filter @workspace/social typecheck` passed after the final owned changes. The final `e2e/frontend-compliance-consent.spec.ts` run passed **11 tests, 0 failed, 0 skipped**, using the synthetic beta build on port 4181; total build-and-run duration was 365.4 seconds under concurrent build load. Evidence: [final structured results](evidence/consent-final.json) and [execution log](evidence/consent-final.log). These tests check public routes/provider deferral, Google failure/retry and responsive resize, registration acceptance, reacceptance failure/concurrency/mismatch, absence of hidden social hydration on version mismatch, analytics persistence/withdrawal/storage denial, withdrawal of an ineligible account's saved choice, and grievance limits/focus. The last two tests bundle the actual telemetry source with only the auth-token provider mocked, to exercise inactive batching behavior without enabling production instrumentation.

The first ten-case run found one incorrect test locator and one real successful-acceptance navigation defect; both were corrected. A subsequent ten-case run passed before the saved-choice withdrawal regression was added, and the final eleven-case run above passed after that change. Initial failures and rerun logs remain in the evidence directory. The consolidated frontend test report records the combined suite results and additional root-owned routing/session checks.

The legacy tests named **Google script failure has an accessible retry without disabling other sign-in methods** and **narrow Google sign-in stays within its panel as the viewport changes** assume automatic Google script loading. Their preserved expectation is superseded by the new **Google loads only after a deliberate choice, supports retry, and resizes on narrow screens** regression. A failure caused solely by the old automatic-loading assumption is reported explicitly, not treated as a pre-existing passing test.
